Model selection guide

This guide explains how to choose a local model for a TokenFrugal role, and how to read the benchmark report and explorer to do it. It describes the method only. It does not list results, because those change with each run; the report shows the current numbers.

1. Pick the role first

TokenFrugal has two local roles. A model is only comparable within the role it is tested for.

  • Builder: writes or edits code and files. Scored on write_function, fix_bug, write_tests and rename_across_files. It needs write and edit tools.
  • Thinker: reads, analyses and browses. Scored on 12 cases, from find_symbol and review_sqli to browser_navigate_snapshot and web_crawl. It needs read and search tools, plus the tools of its specific role (browser, design, docs or planning).

The report's Builder and Thinker columns show each model's score on its own role's cases only. Use those columns, not the overall score, to compare models for one role.

2. Check the gates before the ranking

A model that fails a gate is not a candidate, however high its score. Each gate maps to a column or flag in the report.

Valid cases. The run must finish all of its cases without infrastructure failure. The Valid cases column shows this. Partial runs are not ranked.
No infra flag. A ⚠infra mark next to the model name in the Ranking table means the run was affected by the environment (backend down, timeout), not by the model. Rerun before trusting it.
Fits in GPU memory. Shared memory GB above 0 means part of the model runs in system RAM. It still works, but it is slower and its speed numbers are not comparable with fully-GPU runs.
Current code. The Code (git) column shows the commit that produced the run. Prefer runs from the current code, since the router and prompts change over time. The per-role tables compare each model across all of its runs, so check the Latest run and Code (git) columns to see which code produced the numbers.
Required tools. A ⚠ on a case means the case needs a tool the model failed to call. A model that fails required tool cases cannot do that role, even if its pass rate looks reasonable.

3. Qualify a thinker

  • Every thinker case passes in every repeat. Thinker work is read-only, so a missed read or wrong answer is the failure to look for.
  • Tool-call cases matter most. The cases plan_status, design_overview and browser_navigate_snapshot require the tools plan_status, high_level_overview and navigate_page. security_file_read checks that the model respects file-access limits.
  • Consistency across repeats. A case that passes once and fails once is unstable. The per-case heatmap in the report shows each repeat, so check that the repeats agree.
  • Speed as a tiebreaker between models that pass the same cases.

4. Qualify a builder

  • All four builder cases pass in every repeat. rename_across_files changes several files and must leave them consistent.
  • Verified output only. A case counts when the output passes the checks, not when the model says it is done. A model that claims success without the change is scored as a failure.
  • Test-writing is a separate skill. write_tests is often the first case a model fails, so a builder that passes the other three but not this one may still suit small edits.
  • Speed as a tiebreaker, using s per case and t/s.

5. Rank the candidates

The report ranks models by pass rate first, then speed. The Rank column combines both: 60% pass rate and 40% speed (on a log scale, so very fast models are not favoured over accurate ones). Use it to sort, but check the gates above before choosing.

  • Pass rate (%) = verified checks passed / total checks. Compare percentages, not raw scores, because older and newer runs can have different totals.
  • t/s = tokens generated per second, the main speed metric.
  • s per case = mean seconds per case, a secondary speed metric. It includes tool calls, so it can differ from t/s.
  • Run time = wall clock for the whole run.

Treat gaps of a case or two between runs of similar models as noise. Only the number of runs is small (two or three per case), so a clear lead should hold across repeats.

6. Find the best model quickly

  1. Open the report and read Best model per role. It lists the top five for builder and thinker separately, comparing each model across all of its runs. Each model has a colored dot: 🟢 preferred, 🟡 usable, 🔴 not recommended. The full list of models per role is in the collapsed "Show the other models" block under each table, and the preferred choices (more than one per role) are listed under the tables.
  2. For a closer look, open the explorer. Set role to builder or thinker, set Runs from to the last 30 days to see current code only, and sort by Rank.
  3. Apply the gates in section 2 to the top rows: valid cases, no infra flag, shared memory 0 GB.
  4. Among the rows that pass, pick the one with the highest pass rate. Use t/s to break ties.
  5. Check that its repeats agree on every case of the role.

7. Confirm on your own machine

Results depend on hardware and on the model's quantisation. Before you assign a model in router/agents.yaml, run the benchmark on your machine. The steps are in the technical guide and the method is described on the report page. Your run's row appears in the explorer with your machine's details.

8. What the benchmark does not measure

  • General quality outside the 16 cases.
  • Very long contexts. The cases are short, so they do not test each model tag's context limit.
  • Models served by an engine other than Ollama. Results are for the local Ollama setup only.
