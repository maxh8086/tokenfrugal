# Benchmark scripts

Flow: **run → CSV → report → cloud review → Observations in `Benchmark.md`**.

| Step | Command | Output |
|---|---|---|
| 1. Check your hardware | `python Benchmark/script/hardware.py` | GPU / VRAM / RAM / Ollama version |
| 2. Benchmark a model | `python Benchmark/script/run_benchmark.py qwen3:8b [thinker] --n 3` | one row appended to `results/benchmark.csv` |
| 3. Rebuild report | `python Benchmark/script/build_report.py [--run [MODEL ...]] [--n 3] [--update ask\|yes\|no]` | tables + charts in `Benchmark.md`, `explorer.html`; `--run` first does a fresh benchmark run (no names = every local model in `benchmark.csv`); afterwards it asks "Update recommendations? [y/N]" and on yes runs `update_recommendations.py` |
| 3b. Update recommendations | `python Benchmark/script/update_recommendations.py [--dry-run]` | sets `RANKED`/`DOTS` in `ui/index.html` and the default models in `router/tf-roles.yaml` from all data in `benchmark.csv` |
| 4. Cloud review | give the prompt below to Claude / Codex / any API | updated `## Observations` |

Prerequisites: the repo `.env`, Ollama (or an OpenAI-compatible endpoint) with the model pulled, Docker MCP
profiles installed (`python scripts/doctor.py` lists what is missing). Run from the repo root.

- `results/benchmark.csv` holds the local runs and `results/cloud.csv` holds the cloud (`claude-*`) runs, both with the same header. `build_report.py` merges the two; never edit the generated block in `Benchmark.md` by hand.
- Cloud endpoint: add `--endpoint https://api.anthropic.com/v1 --api-key-env ANTHROPIC_API_KEY` (export the key in your own shell; it is never printed). The hardware column becomes `cloud:<host>`. Append cloud rows to `results/cloud.csv`, not `benchmark.csv`.
- Context mismatch: a cloud model has ~200k context against 16k local. Compare scores and `context_used_peak_tokens` (the window a run needed), not seconds.
- A preflight (Docker, MCP profiles, Neo4j, endpoint, models) runs first and stops with a fix command on any failure.
- Mount: cases use `/workspace/<project>/bench/scratch`, so profiles must mount the parent of the repo; the script forces `CC_WORKSPACE` to it and the preflight verifies each profile (fix: `python scripts/install_profiles.py --workspace <parent>`).
- Neo4j: the plan-store backend stops when the last router process exits; start it with `scripts/mcp_up.ps1` (or `.sh`) before a run.
- Other models: `python Benchmark/script/run_benchmark.py <builder> [thinker] --tag <name>`, then step 3. Steps in `Benchmark.md`, section "Haiku baseline and testing your own model".
- Live tool-call check: `python tests/test_haiku_toolcalls.py` (needs `ANTHROPIC_API_KEY`; Haiku can occasionally pick a different tool, re-run once before treating a single FAIL as a regression).
- Data retention (`csvstore.py`): every run is first appended to `results/runs.jsonl` (append-only, never rewritten), the raw JSON stays in `results/raw/` (its name is stored in the `raw_json` column), and the target CSV is copied to `<csv dir>/backups/` before each rewrite. The script refuses to write (and leaves the CSV untouched) when the CSV header has duplicate or unknown column names or any row has a different width than the header; the run is still kept in `runs.jsonl`. Narrower older headers are migrated by column name, never by position. Use a new `--csv` file if you want a different layout.
- `run_benchmark.py --from-json bench/<stamp>-<tag>.json` imports an earlier run without re-running.
- Each case cell is `verified/n`; a case only counts as verified when the output is checked (file diff, test run, expected text), not when the model claims success.
- Compare runs only when they were measured on the same GPU (the report states the test GPU at the top).

## Cloud review prompt

> Read `Benchmark/results/benchmark.csv` and the generated tables in `Benchmark/Benchmark.md`. Do not edit the
> `<!-- BEGIN:auto -->` block. Rewrite only the `## Observations` section: (1) which model wins per role and why,
> (2) speed/quality trade-offs and the smallest model that holds at least 75% of the best score, (3) models to drop
> (score under 50% or 0/32), (4) anything new since the last review (new rows, hardware differences), (5) one
> recommended default builder/thinker pair for the test GPU stated in the report. Cite run tags and numbers from the CSV; do not
> invent figures. Keep it under 40 lines, then run `python Benchmark/script/build_report.py` to confirm the file still builds.

## Coding suite (L1-L6)

Full run: `python Benchmark/script/run_benchmark.py --model <tag> --role builder,thinker,hard,coding` (or `BENCH_SUITE=coding python -m scripts.bench --only realworld` for the coding suite alone). Any subset of roles works, e.g. `--role builder` or `--role hard`; `--metadata` refreshes the hardware and params columns, alone or with roles.
Six cases, one role and Docker MCP profile per level (`profiles/code-l1..l6.yaml`, generated by `scripts/gen_code_profiles.py`, at most 6 tools each):

| Level | Role | Tools added | Case |
| --- | --- | --- | --- |
| L1 | coding-l1 | read_file, write_file, run_tests | fix a swapped-branch bug |
| L2 | coding-l2 | + edit_file, search_files | implement a function |
| L3 | coding-l3 | + directory_tree | add a parameter across two files |
| L4 | coding-l4 | ast-grep | rename a symbol across callers |
| L5 | coding-l5 | + git_diff, sequentialthinking, run_python | debug from a failing test |
| L6 | coding-l6 | synaptree graph tools | change a signature and update callers |

Each check re-writes the test files and runs `unittest` in a network-less `python:3.13-slim` container. Results go to `results/coding/`, never `benchmark.csv`.
